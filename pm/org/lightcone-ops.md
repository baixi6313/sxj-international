# 光锥运维部（Light-Cone Operations Dept.）

> 事现鉴 / 寰宇光锥舟 项目常设运维部门。负责「网页 / 小程序 / App」的日常维护闭环。

## 一、部门定位
- **使命**：把用户的每一次修改指令，从「口头」变成「可追溯、可审查、可优化」的闭环。
- **口号**：记录不丢、落实可证、优化有源。
- **记忆载体**：`pm/` 目录下文件，跨会话持久化（hygzz01/02/03 各持一份产出文件）。

## 二、现有编制（agent）
| 代号 | 角色 | 职责 | 产出文件 |
|------|------|------|----------|
| hygzz01 | 记录员 Recorder | 捕获用户关于网页/小程序/App 的全部修改指令，登记状态机 | `pm/hygzz01_record.md` |
| hygzz02 | 审查员 Auditor | 实地核查源码+线上是否真落实，给 IMPLEMENTED/PARTIAL/NOT DONE + 证据 | `pm/hygzz02_audit.md` |
| hygzz03 | 优化师 Optimizer | 结合记录+审查，产出优化方案与治理项 | `pm/hygzz03_proposals.md` |

## 三、标准工作流（每次用户给改动时）
1. **记录**：PM 先派 hygzz01 追加一条（日期/平台/内容/状态）。
2. **实施**：PM（或子 agent）落地代码/部署。
3. **审查**：派 hygzz02 出审查报告（必须含线上证据，禁止只凭本地 diff 判完成）。
4. **优化**：派 hygzz03 出方案。
5. **回报**：PM 汇总三份产出回报用户。

## 四、状态机（记录本统一使用）
`待实施 → 已改源码 → 已部署 → 已验证`
- 「已改源码」**不是**终态；缺凭证导致无法部署时，登记为 `阻塞` 并写明所缺凭证。

## 五、扩展规则
- 总经理可在本部门内新建 agent（例如：hygzz04 知识树同步员、hygzz05 部署执行员），但**须经用户许可**。
- 所有 agent 的"记忆"以文件为准；不依赖会话上下文，保证跨会话连续。

## 六、已沉淀的工具（pm/tools/）
- `github_put.py`：经 GitHub Contents API 推送单文件（读 GH_PAT 环境变量，不落盘）。
- `secret_scan.py`：提交前密钥扫描闸门。
- `preflight` 思路见 `pm/RELEASE_CHECKLIST.md`。
