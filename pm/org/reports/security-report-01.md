## 一、安全事件回顾：12 个脚本硬编码明文 GitHub PAT

**结论**：明文 PAT 目前**限于本地磁盘**，尚无证据表明已进入公开仓库。这是"未爆炸的弹药"，而非"已发生的泄漏"——但**凭证已在 12 处明文落盘且长期存在，必须按已泄漏处置**（无法排除历史剪贴板、日志、AI 会话记录、备份等外溢路径）。

### 1.4 次生暴露面（本次审计新发现）
1. **12 个脚本未被 `.gitignore` 覆盖**：`git check-ignore` 返回码 1（未忽略）。一次 `git add .` + `git commit` 即会把 12 处明文 PAT 写入 git 历史，且历史一旦推送即**不可撤销**。这是当前最大的"一步之遥"风险。
2. **`.wrangler-cache/hygzz_com/wrangler-account.json` 已入库 HEAD**：内含 Cloudflare `account.id`（`f26b8425…`）与账户邮箱名（`Hakuji817@gmail.com's Account`）。虽非密钥，属**账号标识 + 个人邮箱 PII**，且该路径未被 `.gitignore` 覆盖。
3. **腾讯云凭证：合规**。`tcb_api.py:8-9` 使用 `os.environ.get("TENCENT_SECRET_ID"/"TENCENT_SECRET_KEY", "")`，未硬编码，符合本部门原则。

## 四、建议动作（五项）

### ① 立即吊销并轮换所有泄露 PAT —— P0，24 小时内
1. 登录 GitHub → Settings → Developer settings → Personal access tokens → 找到前缀 `ghp_8fJT…` 的 token → **Revoke**（吊销优先于删除代码，顺序不可颠倒：先断电，再拆线）。
2. 吊销后核查该 token 近期使用记录（GitHub Security log），确认无异常 IP / 异常 Release 操作。
3. 如仍需自动化推送能力，**改签发 Fine-grained PAT**：仅授权目标仓库、仅 `Contents: Read/Write`、设置 90 天有效期。禁止再签发经典 PAT。
4. 新 token **只写入环境变量**（`GITHUB_TOKEN`），由 sc-01 密钥官登记入册。

### ② 全面推行环境变量 / 密钥管理 —— P0→P1
1. 12 个脚本统一改造为 `TOKEN = os.environ.get("GITHUB_TOKEN", "")`，缺失时直接 `sys.exit` 报错，**不得回落到硬编码默认值**（对齐 `tcb_api.py:8-9` 的既有正确范式）。
2. 本地建 `.env`（已被 `.gitignore` 覆盖）+ `.env.example`（仅含键名、不含值）作为团队约定模板。
3. `.gitignore` 追加两条防御：`.wrangler-cache/` 与含凭证脚本的显式路径（在改造完成前先行兜底）。
4. 长期方向：凭证交由系统密钥库 / 云厂商密钥管理服务托管，代码侧只见键名不见值。

> 本节为**建议**，本报告遵守"只读不改码"约束，未执行任何代码修改；改造须由 PM 授权后交对应职能部门实施。

### ③ 提交前强制 secret_scan —— P1
1. 安装 git 钩子：`.githooks/pre-commit` 调用 `python pm/tools/secret_scan.py .`，并执行 `git config core.hooksPath .githooks` 使其对全仓生效。
2. 钩子非零退出即阻断 commit；**禁止使用 `--no-verify` 绕过**，如确需绕过须经安全合规部书面记录。
3. 扩充 `PATTERNS`：补 `sk-[A-Za-z0-9]{20,}`、`AKIA[0-9A-Z]{16}`、`-----BEGIN [A-Z ]*PRIVATE KEY-----`、微信 `AppSecret` 32 位十六进制模式。
4. 每次发布前由 sc-03 审计员执行一次全量扫描，结果归档 `pm/audit/YYYY-MM-DD_security_log.md`。

### ④ 凭证最小权限与可吊销 —— P1，对齐 UAXS
1. 全部对外凭证按 `access-standard.md` §二执行：`scope` 白名单化（read / verify / emit 三选，默认最小集）、强制 `exp`、强制 `jti`。
2. 建立并维护 **CRL 吊销表**（`pm/audit/crl.md`）：记录 `jti`、签发对象、签发时间、失效时间、吊销原因，泄露即刻入表。
3. 参照 Cloudflare User/Account/Zone 三层权限模型（标准 §六已明确其为现实蓝本）划定平台方权限边界。
4. **UAXS 根签名密钥保管方案须先行落定**（离线保存 + 双人保管 + 年度轮换），否则凭证体系不得上线。

### ⑤ 隐私 / 数据合规备案 —— P1，事现涉及真实个人
1. **最小采集**：明确"事现记录"必需字段清单，微信 `openid` 仅作内部唯一标识，不与真实姓名/手机号在同一表存储。
2. **匿名化机制**：对外公开的事现内容中，涉及具体自然人的姓名、单位、联系方式一律做假名化或打码；仅保留 SHA-256 内容指纹用于验证，指纹不可反推原文。
3. **同意机制**：涉个人的事现在提交环节须有明示告知与勾选同意（记录同意时间戳与版本号），并提供**撤回同意 → 下架 / 匿名化**的通道。
4. **争议与更正**：对齐标准 §五 `disputed` 状态，为当事人提供异议申诉入口，异议期内内容标注争议状态。
5. **合规口径成文**：产出《事现鉴隐私与数据合规说明》，对照《个人信息保护法》《网络安全法》《数据安全法》及各平台内容规则，作为发布前置条件（sc-02 合规官牵头）。

## 六、结语

本次审计的核心结论是一句话：**弹药已上膛，但幸而尚未击发**。12 处明文 PAT 至今仍躺在工作区磁盘上未被吊销（P0），而它们没有酿成公开泄漏，靠的不是技术防线，而是"未经许可不推 GitHub"这条决定层铁律——制度替技术挡下了这一枪。这既值得记录，也是警示：**依赖纪律的安全不是安全**。

因此本部门的第一份报告只提一个硬要求：**先吊销，再改码**。吊销 1 枚 token 即可一次性废除全部 12 处暴露面，这是整个项目当前投入产出比最高的一次安全动作。
